# Architecture rules

Read `PROJECT_BRIEF.md` (contract) and `PROGRESS.md` (status) before any change.

- Module layout: `src/domain` (pure Zod models, integrity rules, calculations, imported via `@/domain`), `src/data` (dataset adapters implementing `DataAdapter`, fixtures), `src/state` (pure demo reducer + React provider), `src/ai` (tool contracts/handlers/runner in `tools/`, provider calls only in `*.server.ts`), `src/components` + `src/routes` (UI). Why: enforces the UI / domain / AI separation.
- UI reads forecasts only via `src/state/use-baseline-forecast.ts` (`useForecastView`: domain calls + typed error states); presentation formatting lives in `src/lib/format.ts` and never does financial arithmetic. Why: one path from data to screen, no numbers computed in components.
- Domain types are inferred from Zod schemas in `src/domain/models.ts`; never hand-write a parallel interface. Why: runtime validation and types cannot drift.
- Cash-flow results are daily closing balances from `calculateDailyCashFlow`; never claim intraday liquidity, never convert currencies. Why: only claims the data supports.
- Forecast math sums CashEvents only; invoices link 1:1 to a CashEvent and are never summed. Why: an invoice and its cash event cannot be double-counted.
- Bump `DEMO_STATE_VERSION` in `src/state/demo-state.ts` whenever DemoState's shape changes. Why: hot reload keeps old reducer state; the provider resets mismatched versions instead of crashing.
- Scenarios store absolute adjustments and are always applied to the frozen baseline via `applyScenario`; UI reads baseline + delayed case via `useForecastView`, keyed on `DemoState.revision`. Why: idempotent, non-compounding, reversible what-ifs with fresh recommendations.
- Recovery options are built by `buildRecoveryScenario` from terms in `src/data/recovery-terms.ts`, one independent scenario each (delay + own adjustments), and compared in one `compareRecoveryOptions` pass. Invoice instalments use `split_event`, and `document-links.ts` is the single double-count rule. Why: same-basis, never-combined, conserved comparisons.
- CSV import is preview-then-replace: `previewCashEventCsv` is pure and returns a dataset only when every check passes; only the `replace_dataset` action swaps the baseline and clears scenarios/drafts/agent runs. Why: a cancelled or failed import can never leave partial or stale state.
- Exported free-text CSV cells go through `neutralizeFormula`; the importer reverses it with `restoreFormulaEscape`. Why: no spreadsheet formula injection, lossless round trip.
- Every assistant tool call (live or guided) goes through `runTool` in `src/ai/tools/runner.ts` on a per-request `ToolSession` copy; the browser applies returned changes only via `planAgentRunApply` when its revision is unchanged. Why: one validated, traced, limited path; no shared server state; no stale writes.
- Assistant turns are kept as `DemoState.agentRuns` and stamped with the browser revision on record; UI labels a turn stale when `endRevision` differs from the current revision (only dataset replacement and reset wipe them). Only text history is resent to the model. Why: conversations survive their own constraint changes while old figures are never shown as current.
- Accepted proposals live in `DemoState.acceptedChanges` (own adjustments only) and the active case is always `calculateActiveForecast(baseline, delay, accepted)` via `src/state/active-case.ts`; drafts come only from `buildActionDraft` and may be accepted only when `draftFreshness` is current. Why: accepted changes apply exactly once, never touch actual cash, and stale drafts can never change the forecast.
- Fixture JSON is the single source of truth; the CSV is generated by `bun run fixtures:csv` and a test enforces equality. Why: downloadable files never drift from what the app loads.

- Money is always an integer number of bani (100 bani = 1 RON); never floats. Why: deterministic, exact financial arithmetic.
- Business dates are `YYYY-MM-DD` strings and "today" comes from a fixed demo clock, never the system date. Why: reproducible forecasts and tests.
- Financial calculations live in a pure domain module with no UI, network, storage or AI imports, covered by Vitest unit tests. Why: independently testable, auditable math.
- Keep three layers separate: UI (routes/components), domain (types + calculations), AI/provider adapters (server-only). Why: the AI can never compute or alter financial results.
- AI output may only select tools, request missing input, explain tool results or draft text; numbers shown to users come from domain code. Why: no invented rates, approvals or results.
- Baseline data is immutable; scenarios and accepted changes are layered on top and are reversible. Why: baseline, hypothetical, accepted and actual states must stay distinct.
- Provider secrets are read only inside server handlers from server-side secret storage. Why: credentials never reach the browser.
- Every client-side npm package imported by app code (including new Radix/shadcn primitives) must be listed in `optimizeDeps.include` in `vite.config.ts`. Why: a late dependency discovery re-bundles React mid-session and blanks the open preview.

- Manual ledger edits (add/update/remove a cash event) go through pure `applyLedgerEdit` in `src/domain/ledger.ts` and the `edit_ledger` action, which swaps the baseline and clears what-ifs/drafts built on old data. Why: edits are validated like an import and never leave stale scenarios.
- Delay simulator, solution finder and bank scoring live in pure `src/domain/solutions.ts` (rates in `BANK_TERMS`, labelled demo); `/simulator` keeps its what-if locally and never writes to DemoState. Why: any transaction can be stress-tested without disturbing the guided recovery flow.

- The current app UI lives in `src/biz` (pure model.ts with calculateDailyBalances + localStorage store.tsx) and routes /, /calendar, /transactions, /upload, /agent, /solutions, /bank; older `src/domain`/`src/state` code is legacy and unused by the UI. Why: rebuilt to the Raiffeisen Business AI brief with one shared forecast for every screen.
